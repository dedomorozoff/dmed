# M4 — агенты: план реализации

Только план. Ничего из этого пока не реализовано — пункты закрываются по мере выполнения.

Концепция: агент получает задачу («рефакторни модуль X»), работает фоном, предлагает
серию изменений. Каждое изменение — патч, который проходит diff-review и только потом
применяется. Применение серии — атомарное (всё или ничего, одним undo-шагом).

## Общая архитектура

```
TUI layer                                Core / agent layer
┌─────────────────────────┐              ┌──────────────────────────────┐
│ Agent panel (список      │  msgs       │ AgentManager                 │
│ задач/прогресс/отмена)   │ ──────────► │  очередь задач, жизненный     │
├─────────────────────────┤              │  цикл, отмена                │
│ Diff review (существующий│ ◄─────────── │ Agent (фоновый goroutine)    │
│ ai_review = переиспол.)  │  patches    │  LLM-клиент + инструменты    │
└─────────────────────────┘              └──────────────────────────────┘
        │                                       │
        │ requests                             │ patches
        ▼                                       ▼
┌─────────────────────────────────────────────────────────────┐
│ Apply queue: патчи → валидация → атомарный apply в буфер/файл │
│ (один undo-шаг, один git commit после подтверждения)         │
└─────────────────────────────────────────────────────────────┘
```

Правило проекта: агент никогда не пишет в буфер сам. Он отдаёт серию патчей;
TUI слои приложения решают — дифф-ревью, потом apply.

## Подзадачи (порядок выполнения)

### T1 — Модель задач и очередь (internal/agent)
Создать пакет `internal/agent`.
- `Task` — задача: `id`, `prompt`, `status` (queued/running/review/approved/cancelled/done/failed),
  `progress` (0..1), `created/updated`, `changes []Change`.
- `Change` — одно предложенное изменение: `path`, `orig`/`new` содержимое (для diff),
  либо структурированный патч (`[]diffOp`). Моделируем по образцу существующего
  `internal/vcs.SideBySide` для превью.
- `Queue` — потокобезопасная очередь: `Enqueue`, `Next`, `Cancel(id)`, `Snapshot()`
  (для рендера списка), notify через `internal/events.Bus` (новые события
  `event:agent:status`, `event:agent:progress`).
- Юнит-тесты на FIFO-порядок, отмену, статусы.

### T2 — Фоновый агент (internal/agent)
- `Agent.Run(ctx, task, onPatch)` — goroutine, выполняет задачу через
  существующий `internal/ai.Provider` (переиспользовать `provider.go`).
- Один вызов LLM на задачу (начальная версия, без инструментов/цикла).
  Ответ LLM — серия дельта-патчей (new-old-new структурированно) по конвенции
  системного промпта. Парсер `parsePatches(text) ([]Change, error)`.
- Прогресс: на стриминге обновляем `progress` по числу полученных байт/чанков,
  шлём события. Отмена: `context.WithCancel` из задачи.
- Тесты: парсер патчей, обработка пустого/битого ответа.

### T3 — Apply queue: валидация + атомарность (internal/agent + internal/buffer)
- `Apply(bs []*Change)` — применяем ВСЕ изменения или ничего:
  - сначала валидация: пути существуют, контекст (строки вокруг) совпадает
    с текущим содержимым (защита от устаревшего патча), применяемость патча;
  - затем apply одним логическим шагом.
- Атомарность на уровне текста: используем существующие механизмы буфера как
  единый undo-step (проверить, как `beginChange`/`breakGroup` в
  `internal/buffer/buffer.go` — агентские правки не должны рвать группу набора;
  применить в виде одного патча при помощи одного `InsertText`-цикла, обёрнутого
  в группу).
- Вернуть список применённых изменений для последующего git-коммита.
- Тесты: частичный конфликт (один патч не сходится) → вся серия откатывается.

### T4 — Git + событие сохранения
- После approved-серии: писать изменения на диск (через существующий сейв-путь
  редактора, чтобы не дублировать I/O), затем вызвать git-коммит через
  `internal/vcs` (один коммит на серию: «agent: <prompt первую строку>»).
- Публиковать `EventBufferModified` / `EventFileChanged` в шину, чтобы watcher
  и другие пейны подхватили изменения.
- Тесты: файл меняется, git-статус обновляется, буферы перечитываются.

### T5 — TUI: панель задач + активация
- Хоткей для панели задач (например `Alt+A` уже занят чатом — выбрать
  свободный, mock в `editor.go`, список значений в `handle...`).
- Панель: список задач (id, prompt коротко, статус, прогресс-бар), `j/k` навигация,
  `Enter` → посмотреть/diff первой готовой серии, `x`/`ctrl+c` → отмена задачи.
- Команда в палитре команд (`Ctrl+P`/`F2`): «New Agent Task» — промпт задачи.
- Рендер панели по образцу существующих (git-панель/чат) в `editor/view.go`.

### T6 — Diff review серии (переиспользование)
- Для каждой `Change` из серии — показать side-by-side дифф (переиспользовать
  `internal/vcs.SideBySide` + рендер `diffview.go`).
- Навигация по изменениям серии: `Tab`/`n`/`p` — след./пред. change.
- Accept/Reject аналогично inline-ревью (`ai_inline.go`): `y`/`enter` принять,
  `n`/`esc` отклонить. Accept всей серии — в apply queue (T3).
- Принятие ставит задачу на apply; apply переводит задачу в done/failed.

### T7 — Интеграция конфига
- Расширить `internal/config`: `[agent]` секция: `system_prompt`, `context_max`,
  `diff_context` (сколько строк контекста вокруг изменения). Переиспользовать
  модель/провайдера из `[ai]`.
- Горячая перезагрузка при сохранении конфига (как уже сделано).

## Границы M4 (не входит сюда)
- Рope-структура и мультикурсор — отдельные пункты roadmap (M1), не блокируют M4.
- Инструменты/агентный цикл «действие-наблюдение» (читай-файл, запусти-тест) —
  следующий шаг после M4, отдельно.
- Плагины (M5) — не входит.
